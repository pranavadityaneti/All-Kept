1. Where things stand today

  • The form works locally. Both "Join the waitlist" pills post to /api/interest, which writes to a Cloudflare D1 (SQLite) database through drizzle. Honeypot field, email validation, duplicate-safe.
  • That database only exists on this Mac. Nothing in production. The site's scaffold (vinext + @cloudflare/vite-plugin + wrangler, an .openai/hosting.json) was generated by a site-builder tool and assumes Cloudflare Workers hosting.
  • The product's backend of record is Supabase — Postgres, edge functions (delete-account, sweeper, …), an admin dashboard that reads from it, and a test suite (184 function tests green).
  • No email-sending provider exists anywhere yet. Nothing has ever sent an email from Allkept.
  • The privacy policy does not mention the waitlist. It covers the app, the Instagram account, the backend and "the pages on allkept.app" — but not that the site collects an email address for launch notification. Collecting emails without a sentence about it is a gap.

2. In plain English

Right now the sign-up box saves emails into a scratch database on your laptop. To make it real, the emails need to land somewhere you can see them, that survives deploys, and that we can pull a list from on launch day. The natural place is the same database the app already uses — then the admin dashboard can show "247 on the waitlist" next to your other numbers, and the launch email is one query away.

Two decisions are yours: where the emails live (I recommend Supabase), and where the website is hosted (this changes how the site is deployed, not how the form works).

5. The design (option A)

Table

create table public.waitlist_signups (
  id          uuid primary key default gen_random_uuid(),
  email       citext not null unique,          -- case-insensitive, one row per address
  source      text not null default 'site',    -- 'site-hero' | 'site-footer' | later: 'app', 'instagram'
  ip_hash     text,                            -- sha256(ip + daily salt): abuse tracing, not identity
  user_agent  text,
  created_at  timestamptz not null default now(),
  notified_at timestamptz                      -- set by the launch send; null = still waiting
);
alter table public.waitlist_signups enable row level security;
-- no policies: anon/authenticated cannot read or write; only the service role (edge function) can.

Edge function waitlist

  • POST JSON { email, website, source }. website is the honeypot — if filled, answer "You're in" and store nothing (same trick the current route uses).
  • Validate: trim, lower-case, length ≤ 254, RFC-shaped. Reject anything else with 400 and a plain message.
  • Insert with on conflict (email) do nothing; answer { joined: true } or { joined: false, message: "You're already on the list." }. Never reveal more than that (no count of who else signed up).
  • Rate limit: at most 5 inserts per ip_hash per hour, counted in the table itself — no extra infrastructure. Over the limit → 429 with a friendly message.
  • CORS: allow only https://www.allkept.app, https://allkept.app, and http://localhost:3000 in dev. The anon key is the only thing the browser holds, and the function does not trust it for anything.
  • Tests: valid insert, duplicate, honeypot, malformed email, rate limit, CORS preflight — in supabase/functions/tests/waitlist.test.ts, same harness as the others.

Site

  • WaitlistForm.tsx posts to ${SUPABASE_URL}/functions/v1/waitlist with the anon key in the header; passes source: 'site-hero' | 'site-footer' so we learn which pill converts.
  • Delete app/api/interest, db/, drizzle/, drizzle.config.ts, and the D1 binding from vite.config.ts. The site ends up with no database of its own.
  • Messages stay as they are: "You're in. We'll let you know first." / "You're already on the list." / a plain error.

Admin dashboard

  • A Waitlist page: total, signups per day (last 30), a searchable list (email, source, when), and Export CSV. Read through the existing admin-dashboard edge function so the dashboard's role model applies unchanged.
  • Overview tile: "On the waitlist: 247 (+12 today)".

Privacy policy

One new paragraph, for your approval, under "What we collect" — roughly: "If you join the waitlist on allkept.app we keep the email address you give us, when you gave it, and a hashed form of your network address to stop abuse. We use it to send you one email when Allkept opens, and to nothing else. You can ask us to remove it at hi@allkept.app." This goes through the same verify-verbatim path as the rest of the policy: edit docs/privacy.html, re-extract, verify, copy.

7. Later: the launch email

"One email when it opens. Nothing else." Not needed to collect — needed on launch day. Rough shape, for a later plan of its own:

  • A sender: Resend is the least ceremony (an API key, SPF/DKIM records on allkept.app, ~$0 at this volume). Not a mailing-list product — we keep the list; it only delivers.
  • An edge function send-launch-email that reads waitlist_signups where notified_at is null, sends in batches, sets notified_at, and can be re-run safely after a failure.
  • Rehearsal: send to a list of one (you) first. Then the real run on your Yes.
