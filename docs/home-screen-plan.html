Allkept home screen — what else it could show

Written 12 September 2026 from the code as it stands. Purpose: the home screen today is a rail, a paste field and a category grid. This is the menu of everything else it could honestly be, what each one would cost, and the three I would build first.

1. What home shows today

Everything below is read from apps/mobile/app/(tabs)/index.tsx and the files it imports. The order is the order down the screen.

WhatWhere it comes fromBehaviour worth knowing

Three things about today that matter for anything new

  • The bell and the rail are the same query. /activity ("Notifications") calls the identical useRecentSaves hook — the same 12 newest saves, grouped by day, with a status line. It is not a notification log; it is the rail again, vertically.
  • The category grid already carries three things that are not categories. library_facets_v2 labels a save through item_category_label, which returns Needs attention, Uncategorized or Sorting when there is no category yet. Those come back as category values, so they become tiles — with the generic "Other" artwork, because categoryStyle() has no picture for them.
  • Home is still on the old read. Home calls library_query_v2; Library moved to library_query_v3. v3 is the one that understands dates (since), creators (authors), shapes and flags. Any date-based or creator-based section on home needs home to move to v3 first — a one-line change in lib/home.ts, not a migration.
In plain English. Home today is: your logo and two buttons, a nag to connect Instagram, a row of platform logos, the last eight things you saved, a box to paste a link, and six category cards. The bell at the top shows the same eight things again in a list. Nothing on the screen tells you anything you did not already know two seconds ago.

Search terms—NOT POSSIBLEDeliberately not stored. The search event records only the term's length and the number of results. "Your recent searches" would have to live on the phone, or become a change to the privacy policy.
Which save you opened, and whenitems.opened_atNEW CAPTUREThe column exists in the schema and is never written by anything. item_open is recorded with no properties at all, and open_original records only the platform. So today the system knows that saves get opened and has no idea which. Everything shaped like "you never opened this" is blocked on this one small change.
Dwell time, scroll depth, "was it seen"—NOT POSSIBLENothing measures it. Adding it would be genuinely new behavioural collection and a privacy-policy change — and it is the kind of measurement the app's "no tracking" position exists to avoid.
Anything fetched from a platform—NOT POSSIBLENothing on home may reach out for data a save does not already hold. That is the platform-terms line in the legal plan (§2) and it rules out trending, view counts, "is this still live", creator follower counts, and anything about other people's saves.
A real inconsistency, found while reading. Two parts of the system disagree about what "needs you" means.
  • The push notification (_shared/pipeline.ts) says needs-you = no_link or preview_unavailable. It deliberately says nothing about pending or failed, because both are still being retried.
  • The library filter (needs_attention in library_query_v3) says pending, failed, no_link, or classification failed — and excludes preview_unavailable.
They overlap on exactly one case. If a "Needs you" section lands on home reading the existing flag, it will count saves that are 20 seconds old and still working, and miss the ones the person was actually notified about. This has to be settled before that section is built, and settling it changes Library's filter too — so it is a decision, not an implementation detail.

3. Candidate sections — twelve of them

The four promises each one is measured against: sorted for you · find it again · ready when you need it · calm (no ads, no tracking, no feed). The last one is not decoration — it is written into the store submission and the privacy policy, and it is the thing that rules candidates out.

A. "Start here" M

The five doors as one small board, each row showing whether it is open: Share from any app · Paste a link · Instagram — send to @allkeptapp · A YouTube playlist · Bring in your Instagram history. It replaces today's single "Start with Instagram" card, which appears for anyone without a linked Instagram account no matter how many saves they already have, and never mentions the share sheet — the door that was just built, works everywhere, and needs no approval from anyone.

Why home, not Library. A person with nothing saved has an empty Library by definition. Home is the only screen they will look at, and the first week is the week the habit either forms or does not — which is precisely the number Phase 0 says decides whether to keep going.

Promise
Calm, and sorted for you — it says "here is how this works" once, rather than nagging about one platform forever.
Data
HAVE IT connected_sources (both kinds — today only the Instagram row is read), imports, and a count of items by captured_via. All owner-readable; no migration.
Size
M — the reads are trivial; the work is the copy, the artwork and deciding when each row is "done".
Risks
A checklist that never completes becomes a permanent nag. It must retire itself — a rule like "gone once three doors have produced a save, or once there are 15 saves". Also: the Instagram door only works for Meta-approved testers until App Review lands, so that row must not read as broken.

B. "Needs you" S

One quiet row, above everything, when and only when there is something a person can actually do: "3 saves need a link", "1 could not be read". Tapping goes to Library with the matching filter already applied. Invisible at zero.

Why home, not Library. It is a filter in Library today, behind a sheet. Nobody opens a filter sheet to discover there is work waiting. And this is the section that makes the app trustworthy: it is the app admitting what it could not do, instead of the person finding a blank card three weeks later.

Promise
Sorted for you. It closes the loop that the notification opened.
Data
HAVE IT facet flag=needs_attention gives the count; the flags argument to library_query_v3 gives the list. But the definition has to be fixed first — see the warning in §2. As written, the flag counts saves that are still being worked on.
Size
S — a row, a count, and a route. Half a day, plus the decision about the definition.
Risks
Shouting about a save that arrived 20 seconds ago. Splitting "still sorting" from "actually stuck" is the whole job. Second risk: it duplicates the "Needs attention" tile the category grid already shows (see §4).

C. "This week" S

The rail, but honest about what it is: everything from the last seven days, with the count in the header — "This week · 11 saves". Below seven days old it is what the rail already shows; above it, it is a real boundary rather than an arbitrary eight cards.

Why home, not Library. Recency is the one cut of the library that a grid sorted newest-first answers badly: you have to scroll and guess where the week ends. A header with a number answers "have I saved much lately" in one glance — and for someone building the habit, that number is the feedback.

Promise
Find it again.
Data
HAVE IT — library_query_v3(since => now() - 7 days). Requires home to move off library_query_v2, which is a one-line change in lib/home.ts.
Size
S — a different query and a header.
Risks
This replaces the Recent saves rail; it must not sit beside it. A quiet week shows an empty section, so it needs a fallback ("nothing this week — here's what you saved last") rather than a blank.

D. "A year ago today" S–M

Two or three saves from the same few days in a previous year, changing once a day. Before the app is old enough to have a year, the same section reads "Three months ago" or "Your first saves". Never more than three cards, never scrollable, never refreshed by pulling.

Why home, not Library. This is the AI-recall promise from the welcome concepts, and it is the only one of the twelve that gives a reason to open the app when nothing has happened. It is also the safest version of resurfacing: bounded to three, driven by the calendar rather than by a ranking model, and impossible to scroll into a feed.

Promise
Ready when you need it — the promise the proposal warned about when it said that without resurfacing the app becomes another graveyard.
Data
HAVE IT — a date window through library_query_v3: since for the floor, the before cursor for the ceiling. (Inferred from the SQL; no code does a windowed read today.) lib/activity.ts already has the calendar-day arithmetic, including the midnight edge case.
Size
S–M — the query is small; the date arithmetic and the "not old enough yet" fallbacks are where the care goes.
Risks
Empty for a new library, so the fallback ladder has to be designed, not bolted on. It can resurface something a person saved once and never wanted — which is an argument for letting a card be dismissed. And it must never grow a "show more".

E. "Saved, never opened" M

Three cards, saved more than a couple of weeks ago, never once opened. The single line the whole product was pitched on: "12 things you saved and never opened."

Why home, not Library. Library can only show what you ask it for. This is the thing you would never think to ask for, which is exactly why it is the section that changes behaviour.

Promise
Ready when you need it.
Data
NEW CAPTURE — not buildable today. items.opened_at is in the schema and nothing ever writes to it; the item_open event carries no item id. The fix is small — write opened_at when a save's detail screen opens, which the owner is already allowed to do to their own row — but it is a new fact recorded about a person, so it belongs in the privacy-policy pass rather than slipped in quietly.
Size
M — the capture change, plus a decision about history: every save that exists today has never been "opened" as far as the column knows, so the first render would offer the entire library. It needs a floor (only saves made after the change counts) or an honest label.
Risks
The easiest of the twelve to turn into a feed — the discipline is three cards, full stop. Tone: "you never opened this" can read as a scolding; "still here when you want it" is the same fact without the finger-wagging. And it is the one candidate that needs the policy checked first.

F. "To watch · To try · To go" M

Three or four chips grouping the library by what you would do with a save rather than what it is about: things to watch, things to try (a recipe, a workout), places to go, things to buy, things to read. Tapping opens Library narrowed to that group.

Why home, not Library. "What should I cook tonight" and "what should I watch" are the two real questions, and neither maps onto a category. It is the clearest step beyond the grid without inventing anything.

Promise
Sorted for you — the strongest version of it, because nobody tagged anything.
Data
SERVER WORK — item_ai.actionability is already written for every save by the classifier, with the values watch, try, buy, go, read, reference, none. It is simply absent from library_query_v3's returned columns and from the facets, so the app has never seen it. Adding a column and a facet row exposes it. No new AI calls, no new collection, no extra cost.
Size
M — a migration (one new function version of the query and the facets), the app-side chips, and the Library filter group to match.
Risks
Unlike category, actionability has no correction path — category corrections are stored in user_category beside the model's answer, and there is no equivalent column for this. A save filed under "to buy" that you cannot move stays wrong forever. Second risk: home already has platforms and categories; a third way of slicing the same library may be one too many.

G. "Where your saves come from" S

The platform pills home already has, with the counts switched back on — and, for a library big enough to be interesting, one line underneath: "43 from Instagram · 12 from YouTube · 4 from TikTok".

Why home, not Library. It is already on home; it just refuses to say anything. Platform is the first cut anyone makes, and the counts are the difference between decoration and information. This is a change to an existing section rather than a new one.

Promise
Find it again.
Data
HAVE IT — facet platform already returns the tallies; home passes showCounts={false}.
Size
S — a prop and some copy.
Risks
Almost none. The counts were hidden on purpose ("home is a glance rather than a workbench"), so this is a reversal of a deliberate choice rather than a fix — Pranav's call.

H. "People you keep saving" M

The three handles you have saved from most, each opening Library narrowed to them. People remember "the guy who does the one-pan dinners" long before they remember which category he landed in.

Why home, not Library. There is no creator filter in the app's filter sheet at all today, so there is nowhere else for this to live. And it is a recognition control — you spot the name, you do not have to recall it.

Promise
Find it again.
Data
SERVER WORK — library_query_v3 already accepts an authors array, so filtering is free. There is no author facet, so the top-three counts need a counting query added. Counting client-side over one page of saves would be wrong, not approximate.
Size
M — a facet or a small dedicated RPC, plus the section.
Risks
author_handle is null for a lot of saves — a link with no readable page, an Instagram post with no permalink, an imported entry. So the list can be thin, or dominated by whichever platform reports handles best, which reads as a bug. It also shows nothing on the phone about who those people are beyond a handle: no avatars, because fetching one would be reaching out to the platform for data the save does not hold. NOT POSSIBLE

I. "Ask your saves" S or L

A single tappable line where the search icon's promise currently hides — "What did I save about…" — opening the existing search overlay with the keyboard already up, and three suggestions drawn from the person's own biggest categories.

Why home, not Search. Search is behind an icon. The third welcome concept sells "Ask your saves. Find anything." and then the home screen never repeats it. This is putting the promise where the person lands.

Promise
Find it again — and the AI-recall promise, at least halfway.
Data
HAVE IT for the prompt and the suggestions (facets + the existing overlay, which already does keyword + meaning search). NEW if "ask" is to mean an actual answer — that is a new AI call per question, a new cost per user, and a new line in the privacy policy about what leaves the library.
Size
S for the prompt and suggestions. L for real answers.
Risks
Saying "ask" and delivering a list of results is the kind of gap that reads as broken. Either the copy stays honest ("Search everything you kept") or the feature grows to match the word. Suggestions built from a person's own tags can also put something on the home screen they would rather not have visible over their shoulder.

J. "You saved this twice" S

The handful of things a person sent to Allkept more than once. The strongest signal of actually caring that exists in the data, and it costs nothing to read.

Why home, not Library. It is a filter in Library ("Saved more than once"). As a section it is tiny and high-precision — but see the risk.

Promise
Sorted for you.
Data
HAVE IT — items.save_count, facet flag=repeated.
Size
S.
Risks
For most people this is zero to three items, so it is a section that is empty most of the time — and an empty section is worse than no section. Recommendation: do not build this as its own section. Fold "saved twice" in as a small badge on the card wherever a save appears, or as a tiebreaker inside the Rediscover section.

K. "Bring in your older saves" S

One card, shown once to someone who has never imported, offering the Instagram-history import — and later the TikTok export, per the TikTok plan's Phase 3.

Why home, not Settings. It lives in Settings today, three taps deep, under a heading nobody scrolls to. It is the single biggest one-time jump a library can make, and it is invisible.

Promise
Sorted for you — a library with 400 things in it sorts into something worth looking at; a library with 6 does not.
Data
HAVE IT — the /import route exists and works; imports is owner-readable, so "has this person ever imported" is one query.
Size
S — a card and a read.
Risks
The 7 September decision was that nobody will do the export ritual — request the file, wait a day, download it, upload it. The importer got built anyway. Putting it on home is a bet against that judgement, so it needs a rule for retiring itself (dismissed twice, gone) and it should probably be a row inside "Start here" rather than a card of its own.

L. "Save without opening Allkept" M

One compact, dismissible card teaching the two-tap share gesture, shown to someone whose saves have all arrived by one route — and aimed at the platform they save from most. It disappears the moment a save arrives through the share sheet.

Why home. The whole product depends on that gesture becoming automatic in week one, and the number that decides Phase 1 is exactly this: of the people who saved three things in week one, how many save anything in days 8–14. The share extension was built and proven on the simulator on 12 September (preview builds and your device checklist still to come, per queue item 18) — and nothing anywhere in the app tells anyone it exists.

Promise
Calm — one card, once, that answers a question rather than selling anything.
Data
HAVE IT — a count of items grouped by captured_via tells you which doors this person has ever used. (Inferred: no code reads captured_via on the client today.)
Size
M — the read is trivial; the copy and the artwork are the work, and they have to be good or it reads as an ad.
Risks
Teaching cards are the fastest route to a home screen that feels like an advert for itself. Hard rule: at most one instructional card on the screen at any time, and it must have a condition under which it is gone for good.

4. Recommendation

Build these three, in this order

1. "Needs you" (B) — S, all the data exists. It goes first because it is the cheapest, and because it is the one that makes the app honest: the pipeline already notifies people that a save needs them, and then the app gives them nowhere to land. It also forces the definition question to be settled, which every later section benefits from. Precondition: decide what "needs you" means (see the warning in §2) — it must count only what a person can act on.

2. "Start here" (A) — M, all the data exists. It goes second because the worst moment in the product today is a brand-new home screen: an empty rail, no categories, and a single card that says "Start with Instagram" — a door that, until Meta's App Review lands, works only for accounts added as testers, while the share sheet that works for everyone is mentioned nowhere. Fold K (import) in as a row rather than building it separately, and let L (the share-sheet teaching card) be the one row that survives after the rest of the board has retired.

3. "A year ago today" (D) — S–M, all the data exists. It goes third because it is the promise the welcome screen makes and nothing in the app keeps, and because it gives a reason to open Allkept on a day when nothing has arrived. Three cards, changing once a day, no scroll. When opened_at starts being written, E ("saved, never opened") becomes a second source for the same section rather than a new one — same three slots, better choice of what fills them.

Alongside those, two near-free changes: switch the platform counts back on (G, a prop), and move home from library_query_v2 to v3 so dates and creators are available at all.

What the home screen must not become

  • Not a feed. Not of other people's content — there is no legitimate route to it and it is not what a personal library is — and not of your own either. The test is mechanical: can you scroll it forever? Every resurfacing section gets a fixed number of cards and no "show more". A feed is also the fastest way to turn a calm product into one that needs to be fed.
  • Not an ad slot. "No ads, nothing sold, no cross-app tracking" is written into the store submission and the privacy labels. That includes soft advertising — promoting a paid tier in a section, or dressing a suggestion up as content.
  • Not a notification centre. The bell already goes to a screen called Notifications. Adding a third surface showing the same arrivals would be the third copy of one query.
  • Nothing that reaches out to a platform. No trending, no view counts, no "is this still live", no creator avatars. Anything beyond what a save already holds crosses the platform-terms line in the legal plan §2.

In plain English — what changes for the person. Open Allkept and the first thing you see is whether anything is waiting for you, and if nothing is, you do not see that row at all. Under it is what you saved this week, with a number. Near the bottom, above your category cards, are two or three things from a year ago that you had forgotten you kept. If you are brand new, the top of the screen is a short list of the ways to get things in — including sharing from any app, which the screen currently never mentions — and it goes away once you are using them. Nothing scrolls forever, nothing is advertised, and nothing on the screen came from anyone but you.

6. Decisions for Pranav

  1. The three, and their order. Needs you → Start here → A year ago today, as recommended? Or reorder — Start here first if the priority is new users at launch rather than the people already testing.
  2. What "needs you" means. The push notification and the Library filter currently disagree (see §2). Settling it changes Library's filter as well as home, so it crosses into a feature you did not ask to touch. Approve the scope before it is built.
  3. Do we start recording which save you opened? items.opened_at exists and is never written. Writing it unlocks "saved, never opened" and better rediscovery. It is a new fact about a person's behaviour, so it needs to go through the privacy-policy pass (queue item 15) rather than land quietly. Yes or no.
  4. The bell. It currently opens a screen called Notifications that shows the same twelve saves as the rail. Does it become a real arrivals-and-outcomes log, or does it go away?
  5. Do the three status pseudo-categories leave the grid? Needs attention, Uncategorized and Sorting are tiles today, with the generic artwork. If "Needs you" ships, they are saying the same thing twice.
  6. Is "This week" allowed to replace the Recent saves rail? Replacing is the recommendation; adding it would put two lists of new saves on one screen.
  7. Platform counts back on home? They were hidden deliberately ("home is a glance rather than a workbench"). Reversing that is your call, not a bug fix.
  8. May the home screen ever spend an AI call? Everything recommended is free — dates, counts and statuses. "Ask your saves" with real answers, or a smarter pick of what to resurface, would cost money per person per day and adds a line to the privacy policy. Free-only, or is there a budget?
  9. Actionability (To watch / To try / To go) — build it, and if so does it get a correction path first? Category corrections are stored beside the model's answer; actionability has no such column, so a wrong label would be permanent.
  10. How hard may home push the doors? Proposed rule: at most one instructional card on screen at a time, and each one has a stated condition under which it disappears for good. Agree the rule, or set a different one.
  11. The import card. On 7 September you concluded nobody would do the data-export ritual. Putting "Bring in your older saves" on home bets against that. In, or leave it in Settings?
  12. Does any of this wait for the store submission and Meta's App Review? None of the three needs a native build — they are all JavaScript, so they ship over the air. But they change what a reviewer sees in a screenshot.

Things I inferred rather than verified

  • A date window through library_query_v3. Read from the SQL: since sets the floor and the before cursor sets the ceiling, so passing a timestamp with a maximal UUID should return everything before that instant. No code does a windowed read today, so this has not been run.
  • Reading imports and counting items by captured_via from the phone. The row-security policies allow the owner to select their own rows in both tables, so both should work with no migration. No code does either today.
  • That exposing actionability is only a query change. The column is written by the classifier and stored; adding it to the returned columns and the facets is a new version of two SQL functions. I have not written or run that migration.
  • Section sizes (S/M/L). These are judgements from the shape of the code, not estimates anyone has checked against a calendar.
  • "This will be empty for most people." I have no usage data at all — no idea how many saves a typical tester has, how many are unsorted, or how often anyone saves the same thing twice. Every judgement of the form "this section will usually be empty" comes from the structure of the data, not from measurement. If there are real numbers from the testers, they should be checked before section J or H is ruled in or out.
  • The classifier's vendor in production. docs/store-submission.html §2 already flags this as unverified (the policy names OpenAI; the code picks by whichever key is set). It does not affect anything recommended here, all of which is free of AI calls, but it would matter for decision 8.
