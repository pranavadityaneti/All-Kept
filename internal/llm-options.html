1. The workload being priced

One call per saved link, made from a Supabase Deno edge function in ap-southeast-1, over plain fetch with no SDK. Read from supabase/functions/_shared/classify.ts, openai.ts and classifiers.ts:

  • Input: a fixed 189-word system prompt (1,114 characters) plus platform, kind, link, author, title (≤300 chars), caption or text (≤1,500 chars) and the person's own note (≤300 chars). Short social-media text, often not English.
  • Output: strict JSON — category (one of 15 fixed values), tags, summary (one sentence ≤140 chars, in the caption's language), entities, language, actionability (one of 7), confidence. Today this is enforced by OpenAI's json_schema with strict: true and additionalProperties: false.
  • Measured size: 629 input tokens, 129 output tokens, averaged over 131 real calls (internal/unit-economics.html).
  • Today's cost: gpt-5.6-sol at $4 / $20 per million = $0.005096 per save. A bulk tier gpt-5.6-terra ($2 / $12) is already wired for imports.
  • Retries matter. validateOutput() returns null on anything that does not match the shape, and a failed classification retries up to five times. A model that returns near-JSON instead of JSON does not just annoy you — it multiplies its own bill.

Every "cost per save" in this document is 629 × input_price ÷ 1e6 + 129 × output_price ÷ 1e6, with no caching assumed (the system prompt is identical on every call, so prompt caching is a real further saving on any vendor that offers it — that is a separate lever and is not counted here).

In plain English. You are buying one small, boring job a million times over: read a caption, hand back a tidy little form filled in correctly. It is the same job every time, the text is short, and the answer has to be machine-readable or the whole thing is worthless. That is the cheapest kind of AI work there is — which is exactly why paying premium-model prices for it is worth questioning.

3. The hard requirement: strict JSON

There are three genuinely different things vendors call "JSON output", and the difference decides this whole exercise.

LevelWhat it meansWho has it, verified on their own docs
Strict schema (constrained decoding)The decoder is physically prevented from emitting a token that breaks your schema. Enums are guaranteed. This is what openai.ts uses today. OpenAI (all GPT-5.6 tiers), Google Gemini (responseSchema / responseJsonSchema, enums supported), Mistral (json_schema — "guarantees the message the model generates is in JSON and follows the schema you provide"), Groq (strict: true, on gpt-oss-20b, gpt-oss-120b, qwen/qwen3.8-27b)
JSON object modeYou get syntactically valid JSON. Nothing guarantees your keys, your enums or your types. The model can happily return {"category": "Recipes & Food"} when your enum says "Food". DeepSeek (json_object only, and their docs warn "the API may occasionally return empty content"), Zhipu GLM (text or json_object only), Moonshot Kimi (json_object only, docs give "no guarantees" about matching a schema), Alibaba Qwen on the Singapore endpoint
NothingPrompt and pray.MiniMax M2.x / M3 — response_format is absent from the OpenAI-compatible parameter table and, per MiniMax's own GitHub issue tracker, is silently ignored unverified on an official docs page

The Qwen trap. Alibaba does support strict json_schema — but their own JSON-mode page says it is limited to "Qwen3.7-Plus series, Qwen3.7-Flash series, Qwen3.7-Max series, Qwen3.8-Max series, and Qwen3.8-Flash series models", and then adds: "Singapore region models are not supported yet." Your edge function runs in ap-southeast-1 and Allkept's backend sits in Mumbai. Getting strict JSON out of Qwen means using the Beijing endpoint — i.e. sending users' saved content into mainland China. That is not a trade worth making for $83 a month.

Why json_object-only is more expensive than it looks. validateOutput() returns null whenever category is not one of the 15 exact strings, and the pipeline retries up to five times. A model that gets the enum right 90% of the time does not cost you 10% more — it costs you 10% more calls plus a tail of saves that end up uncategorised after five attempts, which is a product failure, not a billing one. Every json_object-only vendor in the table would need a schema-in-the-prompt workaround and a measured failure rate before the cost column above means anything.

In plain English. "Returns JSON" and "returns the exact form you asked for" are different promises, and only four of these companies make the second one. The others will mostly get it right and occasionally hand you a category that doesn't exist, which your code throws away and pays to ask again. That hidden retry bill is why the cheapest row on the table is not automatically the cheapest option.

In plain English. OpenAI already sells a budget version of the same model, it already does the strict-form trick, your code already knows its price, and your privacy policy already names OpenAI. You could switch the free tier to it this afternoon. The only real question is whether it sorts saves well enough — and you have 131 already-sorted saves sitting in the database to check that against.

The schema has to be restated in Google's flavour (responseSchema, different usage field names — promptTokenCount / candidatesTokenCount instead of input_tokens / output_tokens), classifiers.ts's vendor union widens to include "google", and PRICES_PER_MTOK gains a row. Call it a day's careful work, not a rebuild.
In plain English. Gemini is the only serious rival to OpenAI here: it is a further 2.5× cheaper than the cheap OpenAI tier, it does the strict-form trick properly, and Google is already named in your privacy policy for YouTube and sign-in. The catch is the free version — Google reads and trains on anything you send it for free, which is exactly the thing you have promised users you don't do. If you use Gemini, you must pay for it.

In plain English. Renting your own AI machine costs about $800 a month whether one person saves a link or a million do. At your size that is madness, and even at ten thousand keen Indian users it is still worse than just paying the cheap API. Self-hosting is a thing you do when the API bill passes roughly $1,000 a month and you have someone whose job is to keep it up. Neither is true. Revisit at 50,000 active users, not before.

17. Integration cost against ClassifyDeps

The seam is small and well-drawn. ClassifyDeps is one method:

call(system: string, user: string) => Promise<ModelResult>

and ModelResult is { output, refused, model, usage, error }. openai.ts fills it in 86 lines of plain fetch. So "how hard is this vendor" reduces to four questions: does it take an OpenAI-shaped body, does it enforce the schema, what does it call its token counts, and do you have to build a retry loop that does not currently exist.

18. Multilingual quality, especially Indian languages

I am going to be blunt about this section: I could not find what you need. There is no credible public benchmark that measures short-text social-caption classification in Indian languages across the models in this document. I looked. I am not going to construct a ranking out of general-purpose leaderboards and present it as an answer.

What I can tell you, with sources:

  • The gap is real and measured. HinTel-AlignBench (arXiv 2511.15183) evaluates state-of-the-art open and closed models on English-aligned Hindi and Telugu samples and reports "a regression in performance for tasks in English versus in Indian languages for 4 out of 5 tasks across all the models, with an average regression of 8.3 points in Hindi and 5.5 points for Telugu." Every model tested got worse in Indian languages. That is the finding that should shape your expectations: whichever model you pick, Indian-language saves will be sorted less accurately than English ones.
  • IndicGenBench (arXiv 2404.16816, from Google) covers 29 Indic languages, 13 scripts and 4 language families, and is the most serious public Indic generation benchmark I found. It does not cover 2026 model versions and it does not cover classification of social captions.
  • Claims I saw but will not repeat as fact: that Gemini 2.5 Flash is the best performer on Hindi. That came from a search summary, I could not confirm it against the paper itself, and it concerns a model version that is two generations old in this document's own pricing table. UNVERIFIED

What to do instead of guessing

You are sitting on the only benchmark that matters: 131 real saves, already classified by gpt-5.6-sol, with the outputs stored. The honest test is four hours of work and it beats every leaderboard on the internet for this decision:

  1. Re-run all 131 through the candidate (gpt-5.6-luna first) with the identical prompt and schema.
  2. Measure exact-match agreement on category and on actionability — the two fields where being wrong is visible to a user.
  3. Measure the invalid-output rate: how often validateOutput() returns null. On a strict-schema vendor this should be 0. On a json_object vendor it will not be, and that number is the real price difference.
  4. Read the summary field by hand for every non-English save. The prompt requires the summary to be in the caption's language — that is the hardest thing you are asking for, it is the most visible if it breaks, and no benchmark will tell you whether a given model honours it.
  5. Check language is a correct ISO 639-1 code on the non-English ones.

Note the sample is skewed — 54 Instagram and 57 YouTube out of 132, from one test account — so treat it as a smoke test that can disqualify a model, not as proof that one is good enough.

In plain English. Nobody has published the test you actually need, and I am not going to invent a league table to fill the gap. What is well established is that every one of these models is worse at Hindi and Telugu than at English, by a meaningful margin — so budget for Indian-language saves being sorted slightly worse no matter what you choose. The good news is you already own the right test: run your 131 real saves through the cheap model and compare. Four hours of work will tell you more than any benchmark on the internet.

19. Recommendation

Switch the free tier to gpt-5.6-luna. Nothing else, yet.
$0.000281 per save — 18× cheaper, $5,096/month down to $281/month at 10,000 Indian users. Zero new code, zero privacy-policy change, zero App Store exposure, strict JSON schema unchanged. Gate it on an A/B against your 131 existing saves.

Why this and not the cheaper rows

The rows below gpt-5.6-luna in the headline table that also pass the strict-JSON gate save you between $109 and $205 per month at the 10,000-user scenario. Against that, each of them costs you a privacy-policy rewrite, an App Store re-disclosure, a new integration to build and maintain, a new failure mode to monitor, and — for most of them — a retry loop you do not currently need. $281/month is already a rounding error against the $99/year Apple fee and a Supabase plan. The 18× step is the one that changes the shape of the business; the further 2–3× does not.

The second choice, if luna fails the quality test

Groq on openai/gpt-oss-20b ($0.0000859/save, 59×), conditional on two things you must check before committing: (a) the Developer-plan rate limits, which Groq does not publish, and (b) the same 131-save A/B. It is the only sub-$0.0002 option with genuine constrained decoding, its schema requirements are identical to what OUTPUT_SCHEMA already satisfies, it is a US company storing in the US, and it offers Zero Data Retention to every customer rather than by approval.

Google Gemini 2.5 Flash-Lite paid ($0.0001145/save, 45×) is the safer-brand version of the same move: better Indic-language prospects than an open 20B model, a vendor already named in your policy, and mature structured output — at the cost of a slightly larger integration and the discipline of never, ever letting a request fall onto the free tier.

What I would not do

  • Do not use any free tier for production saves. Google's free tier trains on user content and says so on its own pricing page. OpenRouter's free endpoints route to providers that train. The two that do not train (Groq free, Z.ai free models) have ceilings or unpublished quotas that cannot carry a product.
  • Do not use DeepSeek, Kimi, Qwen-via-Beijing or MiniMax. Each fails on the strict-JSON requirement, and each additionally fails on jurisdiction, training-by-default, or — in MiniMax's case — on my inability to find a data policy at all.
  • Do not self-host. $796/month fixed, worse than gpt-5.6-luna until roughly 2.8 million saves a month, and it buys you a GPU to babysit. Revisit past 50,000 active users.
  • Do not touch the paid US tier. unit-economics.html is right that paid users are not the problem. Keep gpt-5.6-sol there, at least until the free-tier A/B tells you something about quality.
In plain English. The big win is sitting in a drawer you already own. OpenAI sells a budget model that does everything your code needs, costs an eighteenth of what you pay today, and requires no legal work and no engineering. Point the free Indian tier at it, keep paying full price for the Americans who are paying you, and check the quality against the saves you already have. If the quality isn't good enough, Groq is the next stop — but check their volume limits first, because they don't publish them.

20. The decisions you have to make

  1. What agreement rate is good enough? Before you run the A/B, decide the number. If gpt-5.6-luna agrees with gpt-5.6-sol on category for 90% of your 131 saves, is that a ship or a no? Decide it now, in advance, or you will rationalise whatever number comes back. My suggestion: category agreement ≥90%, invalid-output rate 0%, and every non-English summary in the right language — but the threshold is yours, because it is a product judgement about how annoying a wrong category is.
  2. One AI vendor or two? Staying inside OpenAI means one subprocessor, one policy sentence, one thing to monitor — and you stop at 18×. Adding Google or Groq for the free tier gets you to 45–59× but permanently makes you a two-AI-vendor company: two policies to track, two sets of terms to re-read, two things that can break at 3am, and a privacy policy that has to be re-published before the change goes live (§6 promises exactly that). At these absolute numbers — $281 versus $115 per month — I think one vendor wins, but it is your call and it is the call that decides whether this is a config change or a project.
  3. Does the free tier get a ceiling anyway? Independent of model choice. Even at $0.000281 a save, an unbounded free tier in India is an unbounded liability — it is just a smaller one. unit-economics.html already lists a monthly cap as lever four. Model choice makes the liability affordable; it does not make it bounded. Pick one: a cap, or a deliberate decision to run uncapped with a monitored alert.

A fourth item, smaller but worth queuing: §6 of docs/privacy.html ends with a fragment ("the switch also stops search indexing") that contradicts the paragraph directly above it. Whoever edits that policy for a model change should fix it in the same pass.

In plain English. Three things only you can decide: how good is good enough, whether you are willing to become a two-AI-vendor company to save another $150 a month, and whether free users get a ceiling. Everything else in this document is arithmetic.

What I could not verify — read this before relying on anything

  • Gemini free-tier and paid Tier-1 rate limits. Google's rate-limits page now defers to a per-account view in AI Studio and publishes no table. Third-party blogs give confident numbers for older model versions; I have not reproduced them.
  • Gemini paid-tier log retention period. The terms say "a limited period of time" and name no number of days.
  • Gemini / ai.google.dev processing location. No residency statement on the pages I could load. Vertex AI's residency documentation indicates ML-processing commitments exist only for US and EU locations, but the primary page did not render for me. Treat Gemini as "US/global processing" until confirmed.
  • Whether Gemini's OpenAI-compat shim accepts response_format: json_schema. Not stated on the compatibility page. The native generateContent path is the confirmed one.
  • Mistral: default training setting for a paid API account. The primary privacy-data-controls page 404'd for me twice. Secondary sources disagree about the free "Experiment" tier. Check this yourself before shipping Mistral.
  • Mistral: hosting / processing region for La Plateforme. Not found on any page I could load. Do not write "EU" into the privacy policy on the strength of the company being French.
  • Mistral: whether strict is a field inside response_format, and which models support json_schema. The reference documents type only; the FAQ answer did not render.
  • Mistral rate limits. Not published on the pricing page.
  • Qwen-Flash tier boundaries. The billing page gives ranges ($0.05–$0.25 in, $0.40–$2.00 out) without the cut-points. I used the bottom bracket because 629 tokens is plainly a short prompt, but the boundary is unconfirmed.
  • Alibaba Model Studio data policy and rate limits. Not found.
  • Z.ai free-model quotas and rate limits. The pricing page says "Free" and nothing else.
  • Moonshot Kimi rate limits. Not found.
  • MiniMax privacy policy, data policy and jurisdiction. Not found at all. This is itself the finding.
  • MiniMax silently ignoring response_format. Reported on MiniMax's own GitHub issue tracker and community forum, not in official docs. What is verified is that the parameter is absent from the docs I read.
  • Groq Developer-plan rate limits. The page says they exist and then shows only the free table. This is the single most important unverified number in the document if you pursue Groq.
  • Cerebras: structured-output support, endpoint, rate limits, data policy. Their docs site redirects to the marketing pricing page, which carries none of it.
  • Self-hosting throughput. I found no tokens-per-second benchmark I would stand behind for a specific model on a specific GPU at a specific batch size. The break-even table therefore assumes one GPU suffices — an assumption that flatters self-hosting, and it still loses.
  • Indian-language quality rankings. No credible benchmark exists for short-text classification in Indian languages across these models. The "Gemini 2.5 Flash is best on Hindi" claim is unverified and concerns an old model version.
  • Rate-limit headroom generally. Every "this is plenty" judgement in this document is arithmetic against 1M saves/month ≈ 0.4 requests/second, not against a measured burst. An Instagram back-catalogue import arrives all at once — that is what BULK_MODEL exists for, and it is the shape that would actually hit a limit.
In plain English. Everything above with a source link, I read on the company's own page today. Everything in the list just above, I could not find and have refused to guess. Two of those gaps matter for real decisions: Mistral's default on training, and Groq's paid-tier volume limits. If either of those becomes your plan, that is the first thing to go and check.
