1. Summary — the five things that matter

In plain English

Your instinct is right, but the cause is not what you probably think. The sorter is not randomly broken. Two specific things are wrong, and one of them is a fix you already built and then never switched on for the saves you already had.

Finding 1 — The "show the model the picture" fix works, and 117 of your saves never got it. bug

Plain English: Last week you fixed the sorter so it looks at the reel's thumbnail, not just the caption. It works — the sunflower-field reel that was filed under "Design" is now correctly under "Travel & places". But that fix only applies to saves whose picture arrived after the fix shipped. 117 saves already had a picture sitting on disk and have never been shown to the new sorter. They are still carrying the answer the old, blind, text-only sorter gave them. That is 73% of your library.

The fix: make re-sorting depend on the condition ("this save has a picture the sorter never saw", "this save was sorted by an old prompt") rather than on the moment the picture arrived, so every future sorter change drains the back catalogue by itself. Cost to re-sort all 117 now: about $0.65.

Finding 2 — The fifteen categories have names but no definitions, so identical saves land in different places. bug

Plain English: The prompt hands the model a bare list of fifteen labels and no explanation of what any of them mean. So "a tutorial on using Google AntiGravity" went to Tech & tools, and "a tutorial on using Google AntiGravity in a web design workflow" went to Learning & how-to. Four near-identical "automate a YouTube channel with AI" saves split 1–3 across Tech and Learning. Four "here are N websites every designer should bookmark" saves split 3–1 across Design and Tech. It is not the model being dumb; nobody ever told it where the lines are.

The fix: one line of definition per category in the prompt, plus four or five explicit tie-breakers for the known collisions (Tech vs Learning vs Design vs Money).

Finding 3 — When a save has no words at all, the model guesses "Entertainment" and nothing catches it. bug

Plain English: Ten saves arrived with no title, no caption, nothing. Seven of those also had no picture. The model wrote summaries like "A saved YouTube video with no title or description provided" and filed four of them under Entertainment with a confidence score of 0.20–0.30 — which is the model openly saying "I am guessing". That number is stored in the database and read by absolutely nothing — not the app, not the sweeper, not the library. A 0.20 guess looks exactly like a 0.99 certainty on your screen.

The fix: a confidence floor. Below it, the category becomes "Other" and the save joins the "needs attention" list so you can find it.

Finding 4 — Every YouTube save is sorted from its title alone. weakness

Plain English: All 59 YouTube saves — 37% of your library — have a completely empty body text. The playlist door stores the title and nothing else, and enrichment uses YouTube's oEmbed, which does not return the description. So the sorter judges an hour-long video from a headline. That is where your worst guesses cluster. The pipeline already calls the YouTube Data API for each video (to learn its shape); adding snippet to that same request would give the sorter the description for free.

Finding 5 — You have never corrected a single category, so nothing is learning, and there is no way to re-sort a save. bug

Plain English: There are zero rows where you overrode the model's answer. The override UI exists (the "Put this under" chips on a save), so the wrongness you are feeling is entirely unrecorded — which is why I had to judge the rows myself rather than learn from your corrections. Separately: once a save has been sorted successfully, there is no way to sort it again. The "Retry sorting" button only appears on saves that failed, and the database function that claims work has no branch at all for an already-sorted save. Your only recourse for a wrong category is to tap a chip, which patches the label but leaves the model's own bad summary and tags in place.

2. How sorting works today

In plain English

A save comes in, the server goes and fetches whatever the platform will tell it about the link, stores the thumbnail, then makes one call to an AI model with that text (and, since last week, the thumbnail) and asks for a category, tags, a one-line summary and a confidence score. The answer is written into a separate table so your own correction, if you ever make one, always sits beside it rather than on top of it.

The flow, step by step

  1. Capture. A door creates the row: the Instagram DM webhook (instagram-webhook/process.ts:192), the YouTube playlist poller (youtube-poll/poll.ts:63), a pasted link (save-link/handler.ts:48), or a bulk import (import-saves/index.ts:130). All of them go through _shared/capture.ts:70. Status starts at pending.
  2. Hop to the pipeline region. Each door then calls the sweeper rather than running the pipeline itself, so the work happens next to the database (_shared/enqueue.ts:22, region ap-southeast-1).
  3. Enrich. _shared/enrich.ts:346 expands short links, asks the platform's oEmbed endpoint, falls back to reading the permalink's Open Graph tags, and stores the poster frame into the private thumbs bucket (_shared/pipeline.ts:45 snapshotTo). Result: title, text, author_name, thumbnail_path.
  4. Consent check. _shared/pipeline.ts:233 reads profiles.ai_sorting_enabled. Off means nothing leaves the system.
  5. Claim. claim_item_classification() takes a two-minute lease and returns the fields the model will see, including the picture's path since last week (20260916090000_classify_with_the_picture.sql:11–37).
  6. Read the picture. _shared/classification-worker.ts:21 asks pictureForModel (_shared/pipeline.ts:82) to download the object with the service role and base64 it. JPEG/PNG/WebP/GIF only, 3.5 MB cap; anything else is skipped silently and the save is sorted from words.
  7. One model call. _shared/classify.ts:94 → _shared/openai.ts:46 (default gpt-5.6-sol, reasoning effort low, 20 s timeout, strict JSON schema) or _shared/anthropic.ts:23 (claude-opus-5) when no OpenAI key is set. Imports use the cheaper gpt-5.6-terra (_shared/classifiers.ts:12, selected at _shared/pipeline.ts:241).
  8. Validate. _shared/classify.ts:71 re-checks the category against the fifteen, lowercases and de-duplicates tags, clips the summary to 140 characters, clamps confidence to 0–1. Anything it cannot trust returns null and becomes a retry.
  9. Finish. finish_item_classification() writes item_ai and sets classification_status. On failure it schedules the next attempt on a 60s / 5m / 30m / 2h ladder, five attempts, then failed (20260909113440_classification_retries.sql:66–98).
  10. Display. Everything you see goes through item_category_label(coalesce(a.user_category, a.category), i.status, i.classification_status) — your correction wins, then the model's answer, then "Needs attention" / "Uncategorized" / "Sorting" (20260909113440_classification_retries.sql:121, used by library_query_v3 at 20260910020000_library_query_v3.sql:55 and by the mobile app at apps/mobile/lib/item.ts:75).
  11. Re-sorting. A trigger requeues a save when its watched content columns change, or when a picture lands on a save that was sorted without one (20260916090000_classify_with_the_picture.sql:46–65). The sweeper drains the queue every five minutes in five passes (sweeper/index.ts:39–54).

The prompt as it stands today (_shared/classify.ts:48–58, PROMPT_VERSION = "2026-09-16.1")

You sort things a person saved from social media into their personal library.
Given one saved item (platform, kind, link, title, caption or text, author, the person's own note), return JSON with:
- category: exactly one of ["Food & recipes","Fitness & health","Travel & places","Learning & how-to","Tech & tools","Money & career","Design & inspiration","Style & fashion","Beauty & self-care","Home & living","Entertainment","Humour & memes","News & opinion","Life & relationships","Other"]. Use "Other" only when nothing fits.
- tags: up to five short lowercase tags (single words or hyphenated), specific to the content, no hashtags, no duplicates of the category.
- summary: one plain sentence, at most 140 characters, saying what the item is about, in the caption's language if it is not English.
- entities: places, products, recipes, tools, people or brands named in the content, as {type, name}; empty if none.
- language: ISO 639-1 code of the main language of the text.
- actionability: watch (a video to watch), try (a recipe, workout or how-to to attempt), buy (a product), go (a place to visit), read (an article or thread), reference (facts or tools to keep), none.
- confidence: 0 to 1, your confidence in the category.
Judge from the content only. Hashtags and emoji are weak signals. If the text is empty, use the link, kind and author.
A picture may be attached: the saved post's own poster frame or photo. Captions often describe how a post was made (credits, tools, "edit") or its mood (aesthetic hashtags) rather than what it shows; the picture is the subject, so judge the category from it and treat such a caption as a weak signal. Without a picture, when the caption is only credits, mood or hashtags, prefer the subject if the words let you infer it, else "Other" with low confidence rather than a category for the making.

The message the model gets (_shared/classify.ts:60–66)

platform: {platform}
kind: {kind}
link: {canonical_url or source_url, or "(none)"}
author: {author_name or "(none)"}
title: {title clipped to 300 chars, or "(none)"}
caption or text: {text clipped to 1500 chars, or "(none)"}
person's note: {note clipped to 300 chars, or "(none)"}

That is the whole input. No tags, no platform-specific hints, no examples, no list of the categories already in use in this person's library.

  2. Reddit, 4 saves. Title only; the body of the post is never read.
  3. Pinterest, 2 saves. Literally nothing. Both were sorted into "Other" at 0.10 and 0.15 confidence, which is at least honest.
  4. TikTok, 9 of 10 with no body text.
  5. Instagram is fine on text — the problem there is not absence of caption but the kind of caption: hooks and calls to action ("Comment SKILLS and I'll DM you"), credits and mood hashtags. That is exactly what the picture pass was built to fix, and exactly what 117 saves never received.

4. The taxonomy — fifteen labels, no definitions

In plain English

This is, in my judgement, the largest single cause of what you are seeing. The prompt gives the model a JSON list of fifteen names and one instruction — "use Other only when nothing fits". It never says what any of the fifteen mean, and it never says which one wins when two fit. So the model breaks ties on wording, and near-identical saves scatter.

The built-in fifteen (_shared/contracts.ts:14–18)

export const CATEGORIES = [
  "Food & recipes", "Fitness & health", "Travel & places", "Learning & how-to", "Tech & tools",
  "Money & career", "Design & inspiration", "Style & fashion", "Beauty & self-care", "Home & living",
  "Entertainment", "Humour & memes", "News & opinion", "Life & relationships", "Other",
] as const;

Their definitions in the prompt

There are none. The entire specification of the taxonomy inside the prompt is this one line (classify.ts:50):

- category: exactly one of ["Food & recipes", ... "Other"]. Use "Other" only when nothing fits.

By contrast, every other field in the same prompt is defined. actionability gets a gloss for all seven values ("watch (a video to watch), try (a recipe, workout or how-to to attempt)…"). tags gets four constraints. entities gets a type list. The one field the whole product is named after gets nothing. The alphabetical neighbour to compare against is the icon pass, where the prompt does define its vocabulary and gives worked examples (_shared/entity-icons.ts:26–32) — that pass is the better-specified of the two.

Working as designed today; worth knowing.

5b. Ground truth from your corrections — there is none

In plain English

I was asked to use your own corrections as the ground truth for what is mis-sorted. There are none — not one save in 161 has a user_category. So this section cannot exist as asked, and the per-row judgements in §5c are mine, not yours.

This is not because the feature is missing. It works:

  • apps/mobile/components/ItemDetail.tsx:277–281 renders a chip for all fifteen built-ins plus your own categories, on every save.
  • apps/mobile/lib/item.ts:111–117 useSetCategory upserts user_category, and fires a category_changed metric.
  • The worker genuinely never overwrites it — the conflict list in finish_item_classification excludes user_category (20260909113440_classification_retries.sql:81–84), and the worker re-reads the row afterwards so a concurrent correction wins (_shared/classification-worker.ts:50). That part is solid.

Two honest readings, and I cannot distinguish them from data alone: either the sorting is closer to right than it feels and the wrongness is concentrated in a handful of saves you have noticed but not corrected; or the correction UI is not discoverable enough to be used (it is below the fold on the save's detail sheet, behind the label "Put this under"). Either way, the product currently has no feedback loop — nothing measures how often the model is wrong, even though the code comment at item.ts:110 says that is the whole point of storing the correction beside the answer.

6. Bugs and weaknesses

B1 — The picture pass never reached the back catalogue bug

What happens
117 saves that have a picture stored on disk have never been shown to the picture-aware sorter, and are still carrying the answer the old text-only prompt gave them. Only 28 of 161 saves have ever been sorted with a picture.
Where
supabase/migrations/20260916090000_classify_with_the_picture.sql:46–65 — the requeue trigger fires only on the transition old.thumbnail_path is null and new.thumbnail_path is not null. The migration contains no backfill statement.
internal/superpowers/specs/2026-09-15-classify-with-the-picture-design.md §D5 explicitly deferred the back catalogue: "One-off, on a separate Yes: re-queue the 27 pictured saves below 0.85 confidence". That Yes was never given.
Evidence
145 saves have a thumbnail; 117 of them have item_ai.usage->'picture' null. The prompt-version split is the same 132 / 28. Proof the fix works when applied: 261445cf moved from Design & inspiration to Travel & places on re-sort.
Root cause
The requeue is keyed on a state transition rather than on the condition being wrong. A save whose picture was already there before the migration can never make that transition again.
Class of failure
Any improvement to the sorter — a new prompt, a new model, a new input field — applies only to saves created afterwards. Nothing in the system re-sorts on a version change, so every future fix will leave the existing library behind in exactly this way.
Solid fix
Make re-sorting condition-driven. Extend items_without_ai() (or add a companion items_needing_resort(lim)) so the sweeper also picks up settled saves where either item_ai.prompt_version <> $current or (items.thumbnail_path is not null and item_ai.usage->'picture' is null), ordered oldest first and rate-limited per sweep (say 50). The sweeper passes the current PROMPT_VERSION in. Keep the existing trigger — it gives immediate re-sorts; this is the safety net beneath it. One consequence to accept deliberately: every prompt bump then re-sorts the library at ~$0.0055 a save. Do not patch this by running a one-off UPDATE to requeue 117 rows — that fixes today and leaves the class open.
Size
Medium (one migration + a few lines in sweeper/index.ts).

B2 — The taxonomy has no definitions and no tie-breakers bug

What happens
Near-identical saves land in different categories depending on wording.
Where
_shared/classify.ts:50 — the category line is a bare JSON array with one sentence after it. Contrast classify.ts:55, where every one of the seven actionability values is glossed.
Evidence
d84e93af vs 2945d8b2 (same tool, Tech vs Learning); cefdd524 vs 684e63a5/ae6b7924/46a05341 (automate a YouTube channel, Tech vs Learning ×3); 4d9f4aa2 vs 9dddbbf3/bfdecc6b/7896fc7f (designer resource lists, Tech vs Design ×3); a0673fd3 vs d9701f9f (AI money videos, Tech vs Money); 3bbee036 vs a648f88c (self-improvement, Fitness vs Learning).
Root cause
The model is given fifteen labels and zero semantics, so every tie is broken by surface wording. The same model, given a defined vocabulary and worked examples in the icon pass (_shared/entity-icons.ts:26–32), behaves consistently.
Class of failure
Unstable categorisation across the whole library, for ever, and non-reproducible: the same save can move between two sorts. It also makes any future evaluation meaningless, because there is no written definition to evaluate against.
Solid fix
Write the taxonomy down, in the prompt and in one place only. (a) One line of definition per category, generated from a single constant next to CATEGORIES in packages/contracts/src/index.ts so app, prompt and docs cannot drift. (b) Four to six explicit tie-break rules for the collisions found above — e.g. "a list or roundup of tools → Tech & tools, even when the tools are for designers; a step-by-step lesson or course → Learning & how-to; making money from a channel, app or business → Money & career, even when the method is an AI tool; visual work to look at for inspiration → Design & inspiration". (c) Bump PROMPT_VERSION, which — once B1 is in — drains the whole library onto the new rules by itself. Fixing the prompt without B1 would leave 132 saves on the old rules, so these two ship together.
Size
Medium.

B3 — Confidence is written and never read; low-information saves get a confident-looking home bug

What happens
Seven saves scored below 0.5. Four of them were filed under Entertainment with summaries that literally say the model knew nothing. Nothing anywhere catches this.
Where
_shared/classify.ts:82,90 stores it; a grep across supabase/functions/, apps/mobile/ and packages/ finds no reader. Not in item_category_label, not in library_query_v3, not in sorting.ts, not in any UI.
Evidence
61e757a0 0.25, a8dd250c 0.20, 6dd04c44 0.20, f1ec3f3c 0.30, d82549e3 0.62 — all "Entertainment". Meanwhile 70aa2e3b 0.10 and c0792116 0.15 correctly chose "Other", so the model can do the right thing; the prompt just does not require it.
Root cause
Two halves. The prompt's "Other" escape hatch is written only for the credits-and-mood caption case (classify.ts:58) and never for "I was given nothing at all". And the number the model produces to flag its own uncertainty is discarded by the system that asked for it.
Class of failure
Every low-information save silently acquires a plausible home, and neither you nor the code can tell a guess from an answer. Worse than an empty category, because nothing invites a second look.
Solid fix
Close both halves. (a) Prompt: an explicit rule — "When the title, caption and note are all empty and no picture is attached, you have nothing to judge from: answer Other with confidence at most 0.3. Never choose a category from the platform or the kind alone." (b) Enforce it in validateOutput (classify.ts:71): below a named floor (CONFIDENCE_FLOOR = 0.4), rewrite the category to "Other", so a model that ignores the rule cannot get past the validator. (c) Make it visible: add 'low_confidence' to the flags group in library_query_v3 and library_facets_v2 so these saves are findable and correctable, rather than hidden inside Entertainment. All three together; (a) alone is a patch.
Size
Small (a) + (b); small-medium with (c).

B4 — YouTube saves are sorted from a title alone weakness

What happens
All 59 YouTube saves — 37% of the library — have an empty text column. The sorter sees a headline, an author and a thumbnail.
Where
youtube-poll/poll.ts:63–65 stores the title only, by design. _shared/enrich.ts:456–465 reads YouTube's oEmbed, which returns no description; only Instagram maps the oEmbed title into text (enrich.ts:459). Nothing ever asks for the description.
Evidence
59 of 59 with no_text. Three of the seven sub-0.5 confidence scores in the library are YouTube saves (a8dd250c 0.20, 6dd04c44 0.20, f1ec3f3c 0.30). YouTube saves are also the ones scattered between Entertainment and Learning & how-to.
Root cause
oEmbed was chosen as the metadata source for every platform uniformly, and it happens not to carry a description for YouTube.
Class of failure
Whole platforms silently under-feed the sorter, and nothing measures or reports it. Reddit (4/4 no text) and Pinterest (2/2 nothing) have the same shape of problem.
Solid fix
The pipeline already calls the YouTube Data API for every video, to learn its aspect ratio (enrich.ts:534–544, part=player). Change that one request to part=player,snippet and store snippet.description (first ~1500 chars) as the item's text and snippet.tags into media_meta. No new request, no new key, no new cost. Then close the class: add a cheap assertion to the pipeline log when a settled save has neither title nor text nor picture, so a platform that stops describing itself shows up instead of quietly degrading. Reddit and Pinterest get their own follow-ups, sized separately.
Size
Small for YouTube; small-medium including the log assertion.

B5 — A successfully sorted save can never be sorted again bug

What happens
Once classification_status = 'ready', there is no way to ask for a re-sort. "Retry sorting" is hidden, and the database claim would refuse it anyway.
Where
20260916090000_classify_with_the_picture.sql:26–29 — the claim's status predicate has branches for queued, retry_wait, expired processing and (with p_retry) failed. There is no branch for ready, with or without p_retry.
apps/mobile/lib/sorting.ts:6–8 hides the button accordingly, so the UI is at least honest — there is no false promise, just no capability.
Evidence
160 of 161 saves are classification_status = 'ready'. For every one of them, the only recourse for a wrong answer is a chip that sets user_category — leaving the model's own bad summary, tags and entities untouched and still shown on the card.
Root cause
"Retry" was designed as a failure-recovery mechanism, not as a correction mechanism, so success was treated as terminal.
Class of failure
The product has no manual escape hatch from a bad answer, which is also why B1 was invisible for a week: there was no way to spot-check the fix on an existing save.
Solid fix
Add or (p_retry and i.classification_status = 'ready') to the claim, with classification_attempts reset to 1 on that branch (same treatment as failed), and widen canRetrySorting to any settled save, labelled "Sort this again". Because p_retry only ever arrives from reprocess-item, which checks ownership first (reprocess-item/index.ts:24–26), this opens no new surface. Pair it with a rate limit if you are worried about cost; at $0.0055 a save the risk is small.
Size
Small.

B6 — The picture requeue is one-shot and can be spent on a failed read bug

What happens
If the re-sort triggered by a newly-arrived picture happens to run at a moment when the picture cannot be read, the save is re-sorted from words, its usage is rewritten without a picture key — and because thumbnail_path is already non-null, the trigger can never fire again. The save is permanently stuck sorted-blind despite having a picture.
Where
_shared/pipeline.ts:82–90 pictureForModel returns null (and only logs) for a HEIC thumbnail, a file over 3.5 MB, or any storage error. _shared/classification-worker.ts:21–28 swallows the failure by design. 20260909113440_classification_retries.sql:83 and :88 then replace usage wholesale on both the success and the failure branch, so the record that a picture was ever used is collateral damage of any later re-sort.
Evidence
No confirmed instance in your 161 saves — I am reporting this from the code, not from a row. The conditions are real (thumbs allows HEIC uploads; MODEL_PICTURE_TYPES excludes it) but rare at this library size.
Root cause
The same root cause as B1: a transition-keyed requeue rather than a condition-keyed one. B6 is the second way that root cause manifests.
Class of failure
Any best-effort step that is allowed to silently no-op, while the thing that would retry it has already been consumed.
Solid fix
B1's condition-driven re-sort closes this as a side effect — the save still satisfies "has a thumbnail, was sorted without a picture", so the sweeper picks it up again. Additionally, make finish_item_classification merge usage rather than replace it (usage = coalesce(item_ai.usage,'{}') || excluded.usage), so a failed re-sort can never erase what an earlier successful one recorded. Both changes, not one.
Size
Small, on top of B1.

B7 — Nine saves are frozen with no picture and no scheduled retry bug

What happens
Every row in the database has next_attempt_at = NULL. Nine preview_unavailable saves have neither a stored picture nor a remote picture URL, and no retry will ever run for them. Seven of those were sorted from literally nothing.
Where
_shared/enrich.ts:386–388 — retryPreviewAfterMs is set only when pageRead?.denied is true, which requires that the fallback page read ran and the page was withheld. A page that answers with parseable-but-useless tags yields denied = false and therefore no retry at all. _shared/pipeline.ts:104–107 then writes NULL, and sweeper pass 4 (sweeper/index.ts:52) has nothing to select.
Separately, 856e11b0 is stuck because enrichment exhausted the five-rung ladder while claim_item_classification refuses status = 'failed'.
Evidence
has_next = 0 for all four status groups. The seven wordless saves all have enrich_attempts = 1, so enrichment ran exactly once and never scheduled a second look.
Honest uncertainty
I cannot tell from the data alone which branch produced denied = false for these nine; the enrichment logs would settle it. What is certain is that none of them has a retry scheduled and none can gain a picture by any existing path.
Class of failure
A save can end in a terminal state that nothing monitors and nothing can leave — silently, while looking normal in the library.
Solid fix
Decouple the preview retry from denied: any settled save with no picture at all and enrich_attempts < RETRY_LADDER_MS.length gets the next rung, regardless of why the page taught us nothing. Then give the ladder an honest terminus: when it is exhausted, record the reason in media_meta and let the save appear in the needs_attention facet, so a dead save is visible rather than frozen. Same for 856e11b0: an item whose enrichment is exhausted should be sortable from whatever it does have, or marked as unsortable — not left queued for ever.
Size
Medium.

B8 — Signed-in clients can write every column of item_ai weakness

What happens
authenticated (and anon) hold INSERT and UPDATE on all columns of item_ai, including category, confidence, model, prompt_version, usage and ai_error.
Where
Verified against the live database via information_schema.column_privileges. Compare 20260909113440_classification_retries.sql:117–118, where the same concern on items was deliberately closed with a narrow column grant. That care was never applied to item_ai.
apps/mobile/lib/item.ts:111–117 upserts through this grant; today the payload carries only user_category, so nothing is being clobbered.
Root cause
Row-level security correctly confines a client to its own rows, but nothing confines it to its own columns. The invariant the design depends on — "a correction is stored beside the model's answer, never over it" (item.ts:110) — is enforced only by the current client's choice of payload.
Class of failure
Any invariant held only by client code is one careless payload from breaking, and this one would destroy exactly the data you need to measure how often sorting is wrong.
Solid fix
revoke insert, update on public.item_ai from authenticated, anon; then grant insert (item_id, user_id, user_category), update (user_category) on public.item_ai to authenticated; — mirroring the items grant exactly. Check the RLS policies still permit the upsert path afterwards, and add a row to supabase/functions/tests/rls.test.ts asserting that a client cannot write category.
Size
Small.

B9 — The icon pass overwrites entities with no concurrency guard weakness

What happens
The sweeper's icon pass reads a batch of rows, makes a model call, then writes entities straight back. A re-sort landing in between silently loses the fresh entities.
Where
sweeper/index.ts:84–87 — db.from("item_ai").update({ entities }).eq("item_id", itemId), with no revision or timestamp check. Every other write in the classification path goes through a leased RPC; this one does not.
Evidence
No observed corruption — the window is a few seconds and your library is small. Reported from the code.
Class of failure
Read-modify-write on a row another worker owns.
Solid fix
Guard the write on the row not having moved — carry updated_at through item_ai_missing_icons() and add .eq("updated_at", seen), or fold the icon write into a small RPC that checks it. Not urgent; it becomes urgent the moment B1 makes re-sorts routine.
Size
Small.

Things I checked that are fine

  • fine JSON strictness. Both clients send the full category enum in a strict schema (openai.ts:12–25,64; anthropic.ts:8–21,33), and validateOutput re-checks it server-side (classify.ts:74) so a non-conforming answer becomes a retry rather than a bad row. Zero ai_error rows in 161 saves. Note that classify() passes undefined for the shape (classify.ts:95), which is correct — both clients then fall back to their own OUTPUT_SCHEMA.
  • fine Leases and idempotency. claim_item_classification / finish_item_classification are a proper two-minute lease with a revision guard and a for update lock (20260909113440:38–98). Nothing is stuck in processing, no lease is expired.
  • fine Retry ladder arithmetic. (array[60,300,1800,7200])[attempts] is only reached for attempts 1–4, because the attempts < 5 guard is evaluated first. No out-of-range index is possible.
  • fine Your correction genuinely survives a re-sort. The conflict list in the finish RPC excludes user_category (20260909113440:81–84), the worker re-reads the row afterwards so a concurrent correction wins (classification-worker.ts:49–50), and deleting a custom category returns its saves to the model's original answer rather than orphaning them (20260912210000_user_categories.sql:55–63). This is well built.
  • fine Model tier choice. Everyday saves use gpt-5.6-sol; an imported back catalogue uses the half-price gpt-5.6-terra (classifiers.ts:12, selected at pipeline.ts:241); the icon pass uses the cheap tier (sweeper/index.ts:83). Sensible. Reasoning effort low is a defensible default for a one-shot classification; if B2's definitions do not fix the boundary cases, raising it is the next lever to try, not a bigger model.
  • fine Cost. $0.89 total for 161 saves, $0.0055 each, 698 input / 138 output tokens average. Pictures average 39 KB. Re-sorting the whole library costs under a dollar.
  • fine Privacy of the picture. pictureForModel downloads with the service role and sends bytes inline (pipeline.ts:82–90); no signed URL is minted and the bucket stays private, as the spec promised.
  • weakness What the tests promise. tests/classify.test.ts and tests/classification-worker.test.ts are good unit tests — they pin validation, retry classification, the picture reaching the model, and the usage.picture record. But nothing tests the reset_item_classification trigger, nothing tests that saves which have a picture actually get one, and there is no golden set or eval measuring category quality at all. That absence is why B1 and B2 could both be true for a week without a red test.
  • fine Summaries in the caption's language. Working as written (classify.ts:52). Two saves affected. A product decision, not a defect.
  • weakness captured_via: "import" is not in the type. import-saves/index.ts:138 writes it and pipeline.ts:241 reads it, but CapturedVia (contracts.ts:8) is SourceKind | "share" and does not include it. It works because the comparison is a plain string. Cosmetic today; it will bite the next person who trusts the type. One-line fix, no behaviour change.

7. What to fix first

In plain English

Do the first two as one change, not two. Writing better category definitions without also fixing the re-sort machinery would improve only saves made after the change — your existing 132 would keep their old answers, and you would conclude the fix did nothing.

  1. B1 + B2 together: condition-driven re-sorting, and a prompt that defines its own categories. Add the definitions and tie-breakers, bump PROMPT_VERSION, and extend the sweeper to pick up any settled save whose prompt_version is stale or whose picture the sorter never saw. The whole library converges in a few sweeps for well under a dollar, and every future prompt change does the same by itself. Medium. This is the change that answers your original complaint.
  2. B3: a confidence floor, enforced in the validator and surfaced in the library. Removes five fake Entertainment saves immediately and stops the class recurring. Small.
  3. B4: give YouTube its description. One extra field on a request the pipeline already makes, and it improves the input for 37% of your library. Small.
  4. B5: let a settled save be sorted again. Cheap, and it gives you a way to spot-check every future sorting change on a real save instead of waiting a week. Small.
  5. B8: narrow the item_ai grants. Protects the correction data you are about to start collecting. Small.
  6. B7: unfreeze the nine picture-less saves and the one dead one. Medium.
  7. B6 and B9. B6 is largely closed by B1; the usage merge is the remaining piece. B9 becomes worth doing once re-sorts are routine. Small each.

One thing that is not a code fix

Start correcting categories in the app when you see a wrong one. Right now there are zero corrections in 161 saves, which means neither you nor I have any measured ground truth — every judgement in §5c is mine. Twenty corrections would turn the next audit from "here is what I think" into "here is what you told us", and it is the only signal that can tell you whether the prompt fix actually worked.
